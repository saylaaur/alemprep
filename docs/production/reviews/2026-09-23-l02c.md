## R1 — P1: equal-expiry replay can display a different question from the issued item

Location: `lib/learning/start.ts:142–143`; `lib/learning/service.ts:105–123`.

Two requests for the same actor/operation can read different approved catalogs before either receives a receipt. With the same captured start timestamp, request A selects version A, version A is quarantined, and request B selects/commits version B. The atomic RPC correctly replays B to A. However, its references contain only session/item IDs, mode and expiry. `materializeStartedLearning` compares those with A's locally selected plan; matching expiry and item count pass without verifying the persisted version IDs. It then attaches A's question body to B's item ID and returns before the receipt reader.

The local DB probe uses barriers (no timing sleeps), identical injected server clocks and real RPCs. Both calls succeed with the same session/item IDs, but different question IDs. The stored `session_items.question_version_id` matches the winner, not the stale response. This can make the learner answer a different question from the one the server grades; a later reload also changes the displayed question.

Fix: materialize every successful start from the persisted owner-scoped issuance, or return and strictly compare authoritative version IDs/manifest from the RPC. Expiry equality is not evidence that a locally selected plan won. Preserve the canonical request hash and one atomic RPC invocation.

## R2 — P2: elapsed sessions remain active in the state API

Location: `lib/learning/repository.ts:323–335`.

`decodeLearningState` checks stored `status` but never compares `expires_at` with server time. There is no expiry transition job or SQL update in the current migrations; commit rejects elapsed sessions without changing status. After a valid start, a controlled past-deadline fixture still returns `status: active` with questions. Expected: `{status: 'expired', sessionId}`. Reload/recovery consumers cannot trust this state union and may resume work that submission will reject.

Fix: derive effective expiry using trusted server time for active rows, with tests at/before/after the boundary. Submitted receipts must still take precedence, and cancelled sessions must remain cancelled. Do not change start replay semantics: replay restores the original issuance, while state reports its current effective state.

## R3 — P1: practice can only ever issue the first question in a topic

Location: `lib/content/learning-catalog.ts:118–120`.

Every new practice request sorts by immutable UUID and takes `[0]`. The selector has no operation-dependent selection or learner history. Eight different operation IDs against a two-question approved topic produced eight sessions containing the same question; every further start follows the same code. Once L03 adopts this service, the topic cannot progress beyond its first question. The assessment selector has the same fixed-order behavior for new tests, although this finding is demonstrated on practice.

Fix: distinguish new issuance from replay. Select a fresh/next question for a new operation using bounded server-side history or an explicit persisted selection policy; preserve the original issued items through receipts for retries. Add a regression with multiple available questions and accepted prior attempts. Determinism of retries must not force all independent operations to use the same question.

## R4 — P2: a complete approved catalog can be rejected after the first 160 rows

Location: `lib/learning/repository.ts:255–265`.

The query orders all types together by UUID and limits to 160 before blueprint selection. A synthetic subject with 160 single questions followed by an approved multi and matching question has enough content for the weekly/diagnostic blueprint. The real catalog query returns only singles and the planner returns null (`content-unavailable`). Splitting by subject fixed one truncation case but does not reserve capacity for each required type.

Fix: use bounded reads aligned with the blueprint's required types (and the chosen balancing policy), or another server-side bounded selection that can distinguish true shortfall from truncation. Do not remove the bound or silently shorten the exam. Test a complete catalog larger than 160 and a genuine type shortfall separately.
