### R1 — P2: неизвестная scoring version принимается как trusted результат

Строки 337–339 проверяют равенство строк, но не поддержку `ent-v1`. После штатного start изменить `sessions.scoring_version` на `future-v99` и передать такое же значение в commit: возвращается receipt со `scoringVersion: future-v99`, создаётся одна attempt и начисляется 10 XP. Ожидание — `invalid-input` и ноль новых facts. Некорректное внутреннее состояние проходит DB-границу; текущий receipt decoder такой результат не признаёт.

Исправление: для новой сдачи после receipt replay проверить literal `ent-v1` и у сохранённой сессии, и у RPC input. Старый принятый receipt не переоценивать. Runtime decoding/application wiring остаются L02c/d.

### R2 — P2: разрыв позиций не нарушает manifest и принимается

Строки 340–354 и 421–431 проверяют порядок и количество, но не непрерывность позиций. После start с одним item выполнить `UPDATE session_items SET position=7 WHERE session_id=...`. Manifest остаётся прежним, commit пишет attempt/XP. Constraint в 0024 требует только `position >= 0` и уникальность, а не `0..N-1`.

Исправление: проверить позиции `0..N-1`, count 1..80 и один item для practice. Corrupted denominator тестировать отдельно от `sessions_question_ids_count_check`: NULL total, согласованно изменённые total/question_ids, NULL question_ids. Manifest v1 не менять.

### R3 — P2: пустые UUID молча снимают ограничения выдачи

Строки 115 и 128 используют `NULLIF(value, '')::uuid`. Plan с `topicId: ''` и `subjectId: ''` успешно создаёт дополнительную session. Membership checks в строках 195–196 пропускаются, так как parsed IDs стали NULL. Нарушено требование строгих UUID, ошибка составления plan скрывается.

Исправление: пустая строка — `invalid-input`; разрешённые null/отсутствие обрабатывать отдельно по режиму. Не запрещать null везде: diagnostic/weekly могут использовать другой scope. Тестировать topic и subject раздельно, включая несовпадение только одного из них.

### R4 — P2: quarantine скрывает статус принятой сессии для новой операции

Строки 356–381 проверяют публикацию раньше terminal status. Start → submit → quarantine → submit с новым operationId возвращает `content-unavailable`, хотя §7 требует `{error: 'already-submitted'}`. Прежний результат сохраняется, но клиент получает неверную причину отказа. Повтор того же operationId не затронут: receipt lookup раньше.

Исправление: после ownership/integrity проверки вернуть submitted status до проверок, нужных только для нового принятия. Сохранить ранний same-operation replay/conflict. Проверить неизменность attempt/XP/audit/receipt и отдельный same-op replay после quarantine.
