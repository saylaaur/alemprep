## F1 — P1: programme approval does not serialize with content edits

Location: `supabase/migrations/0031_pilot_access_and_immutability_corrections.sql:223–230` (also programme approval trigger at 239–261).

Both OLD and NEW parent statuses are checked without locking the programme. In transaction B, update an item in a draft programme and leave it open. Transaction A can then approve that programme and successfully publish an assignment using the old committed item set. B remains free to commit the previously checked edit after publication. The reverse overlap also succeeds: while approval is pending, another transaction edits the item based on the still-visible draft status.

Observed: `{published:true, visiblePublishedPosition:0, pendingEditorPosition:42}`. Both transactions were rolled back after observation. A separate pending-approval-first probe also allowed the item edit. This violates the promised frozen programme order, even though sequential move/demotion tests pass.

Fix: use a shared, deterministic parent-row lock protocol for item insertion/update/deletion and approval; recheck status after acquiring locks. Validate the eligible locale/purpose/publications at approval. Add two-connection regression tests for both approval/edit orders, including a published assignment referencing the programme. Changing the item set requires a new programme identity/version.

## F2 — P2: cancellation can rewrite published assignment history

Location: `supabase/migrations/0031_pilot_access_and_immutability_corrections.sql:272–278`.

The replacement trigger permits any UPDATE whose old status is published and new status is cancelled. It never compares the remaining columns. A privileged operator/service write can therefore change the programme, deadlines, revision or school/group scope as part of cancellation. This regresses the old blanket protection and contradicts the claim that scope/window remain immutable. Browser table writes remain revoked; this is a database integrity defect, not a claim of direct student CRUD access.

Reproduced on a genuinely RPC-published assignment: `UPDATE assignments SET status='cancelled', revision=revision+10, due_at=opens_at, closes_at=opens_at ...` succeeds; observed revision 11 and a rewritten window. It produces zero cancellation audit events. The SQL probe was rolled back.

Fix: permit only the status transition while requiring every other persisted field to remain unchanged, and keep legitimate cancellation behind the authorized transactional audit path. Test compound cancellation updates, unchanged history, unauthorized callers and exactly-once audit on retry.

## F3 — P1: concurrent membership revocation produces an empty successful assignment

Location: `supabase/migrations/0031_pilot_access_and_immutability_corrections.sql:346–368`.

Publication locks `group_memberships`, but does not lock the joined student `school_memberships`. It counts eligible students, inserts the assignment, and then rereads membership eligibility in a second statement. A concurrent school-membership revocation can commit between those statements. The response and audit still use the old count, and no zero-row check follows the participant INSERT.

Reproduced with a SHARE table lock on `assignments` as a deterministic barrier: publication counted one student, blocked at assignment insertion, a separate connection revoked that student's school membership, and publication resumed. Result: `{participants:1}` and a successful assignment ID, but actual `assignment_participants` count **0**. Assignment transaction was rolled back; the synthetic membership was restored and setup deleted.

Fix: lock the actual membership rows as well as group links in the shared revocation lock order, and materialize one eligible set for both creation and reporting. Assert the inserted row count. Add a concurrent revoke test rather than relying only on the already-empty-group case.

## F4 — P2: test cleanup disables FK cascades and leaves dangling school data

Location: `tests/db/helpers.ts:220–246`, particularly deletion of `school_memberships` at 240–242.

`session_replication_role='replica'` disables FK triggers, including the cascades that should remove group memberships, teacher assignments and invites when a school membership is deleted. Cleanup explicitly deletes none of those dependents, then deletes their parent memberships. The later auth-user deletion cannot cascade through parents that are already gone. After the fresh full suite, read-only inspection found **35 orphan group memberships, 33 orphan teacher assignments and 8 orphan invites** in the shared local database. Counts include accumulated synthetic state; they are not production data.

There is also no pinned connection/transaction around the session-level SET: `pool.query()` does not promise all statements use the same backend. Avoid relying on session configuration across pool calls.

Fix: perform precise synthetic cleanup on a dedicated connection in one transaction with normal FK behavior; if a narrow immutable-history trigger must be bypassed for fixtures, keep referential cleanup explicit and rollback-safe. Verify no new dangling rows remain, and rerun the DB suite plus historical migration-path suite serially after repairing the harness.

## F5 — P2: CLI does not preserve its default provisioning operation identity

Location: `scripts/pilot/provision-school.ts:62–76`.

The database now supports safe replay, but the CLI generates a fresh `operationId` on every invocation and never prints or persists it. `schoolId` is also regenerated when omitted. After a lost successful response, repeating an ordinary command with a fixed school ID produces `operation-conflict` instead of replay; omitting both IDs on local runs can create a duplicate school. Even a dry-run result returns only the school ID, not the operation ID needed for the next invocation. Explicitly supplying both IDs works, but the advertised defaults defeat the recovery contract R7 was supposed to close.

Fix: require durable school/operation IDs for `--apply`, or save a manifest that dry-run and apply/retry share. Report the IDs before a network mutation without exposing secrets. Test a lost response followed by repeating the exact CLI invocation.

## Resolution in follow-up migration 0032

The findings above are resolved in the pending follow-up, not in `e35194b` itself:

- **F1:** programme item mutations and programme approval acquire the same parent-row lock. Both edit-first and approval-first interleavings are covered; approval also refuses an empty, unpublished, quarantined, or locale-mismatched item set before it becomes immutable.
- **F2:** a published assignment may transition only by changing `status` from `published` to `cancelled`; JSON comparison rejects changes to every other persisted field, including deadlines and revision.
- **F3:** assignment publication locks the eligible group links and underlying active school memberships, then verifies that its participant insert count equals the locked snapshot count.
- **F4:** local teardown now uses one dedicated transaction, explicitly removes each synthetic dependent in FK order, and confines `session_replication_role = 'replica'` to that transaction so it cannot leak through the pool. The regression test checks memberships, teacher links, invites, and parent memberships.
- **F5:** `--apply` requires caller-supplied school and operation UUIDs. Dry-run output includes both generated IDs, so the exact request can be replayed after a lost response.
