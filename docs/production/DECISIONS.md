## Hosting branch H1/H2

**H1: действующий managed контур допустим.** Зафиксировать не только регион Postgres, но Auth, application execution, logs, AI/Desmos и backup. Создать отдельный staging с synthetic seeds; ограничить production keys и преподавателей. Переходить к P01 после документированного решения D02.

**H2: нужен другой контур.** Не писать новый backend по умолчанию. Сначала подобрать провайдера/оператора под PostgreSQL, Supabase-compatible Auth/Data API или документированный Auth adapter, HTTPS, резервирование, мониторинг, обновления и доступ аварийного восстановления. Если managed Supabase недоступен в принятом регионе, ответственная self-hosted установка требует отдельной инфраструктурной приёмки:

1. Новый synthetic кластер: сети/закрытые admin endpoints/TLS, секреты отдельно, external API origin allowlist, storage не публичный по умолчанию.
2. Применить schema и E02/L04/S04 test suites; собрать Next.js как контейнер/standalone при необходимости, проверить SSR cookies, callback URL, proxy headers и лимиты.
3. Backup restore всех используемых сервисов, health, патчи/обновления и дежурный; измерить N/2N на **этом** контуре.
4. Составить manifest переноса: schema, versions, allowed content; перенос существующих персональных данных только по принятому основанию. Старые неподтверждённые результаты не преобразуются в trusted.
5. Auth: перенос паролей/identities/tokens не обещать до проверки совместимости; безопасный вариант — повторный вход/приглашение, контролируемое сопоставление прежнего user ID оператором. Не связывать аккаунты только по произвольному присланному email.
6. Репетиция в изоляции: count/checksum, права, login, expiry, restore. Объявленное окно writes; freeze → финальный перенос → verify → DNS/alias → smoke → наблюдение. Откат маршрутизации только к согласованному writer: не два независимо пишущих контура.

H2 становится отдельным детальным инфраструктурным ticket после выбора провайдера: нельзя дать честные исполняемые команды provision до знания продукта, региона и прав доступа. Это **явная внешняя развилка**, а не разрешение Terra самостоятельно покупать VPS или менять production.

## Вход в школы

Базовый путь — существующий Google OAuth с индивидуальными допустимыми школьными аккаунтами. Приглашение в группу даёт доступ только после входа, само по себе не аутентифицирует ученика. Учитель не выдаёт всем одну учётку.

В D03 проверить ограничения возраста/политику школы, доступ Google на устройстве, потерю пароля и массовый первый вход. Если Google невозможен, до набора нужен отдельный утверждённый способ входа (например, институциональная почта с OTP, если она есть). Не добавлять общий PIN, предсказуемые пароли или fake email аккаунты как спонтанный обход. Конкретная адаптация транспорта Auth не меняет UUID actor, memberships, права и аудит из основной архитектуры; E02/P01 выполняются заново для неё.

## Сроки хранения: параметры реализации, не автоматически выбранное основание

В `retention-policy.json` после D04 записать численные `learningDays`, `auditDays`, `reportDays`, `backupDays`, `technicalLogDays`, `privacyRequestDays` и дату утверждения. Все >0, job отказывается удалять при отсутствующем/неутверждённом policy. Начальная рекомендация для обсуждения: учебная история до окончания пилота плюс 90 дней для отчёта/обращений; технические логи 30 дней; backups 30 дней; audit/report по отдельно принятой цели. Это предложение, не действующий срок.

Отзыв участия сразу выключает school access и новые операции. Удаление проходит проверку заявителя, прекращение сессий Auth и jobs, стирание/обезличивание разрешённых данных, инвалидирование персональных report snapshots; backup естественно истекает по policy и при восстановлении повторно применяет tombstones. Ни псевдоним, ни скрытие repo не делают данные анонимными.
