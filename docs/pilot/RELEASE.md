## Совместимость и оставшиеся риски

1. **0023 и старый main.** Effective grants подтверждают: authenticated не может обновлять XP/стрик. Старый main обновляет эти поля через пользовательский Supabase-клиент, поэтому такой UPDATE отклонится, а сохранение вернёт ошибку. Ветка переносит записи на server-side service-role клиент. Не возвращать клиенту права XP для устранения несовместимости.
2. **0022 подтверждена по схеме.** UUID-массив и constraint существуют; миграционного ledger нет. Старые сессии с NULL остаются без зафиксированного набора. Перед допуском определить срок жизни/завершение старых сессий; не допускать NULL как способ обхода проверки.
3. **Доверенные результаты ещё не обеспечены полностью.** Effective grants подтверждают UPDATE sessions и INSERT/DELETE attempts для authenticated. В `pg_policies` одновременно есть широкие `sessions_own`/`attempts_own` с `ALL` и точечные политики. Проверка владельца не запрещает подмену своего score/is_correct/manifest. Эффективные production-права и поведенческие проверки нужны в блоке 2.
4. **Server actions тоже публичная поверхность.** `createExamSession` экспортируется из `'use server'` и принимает состав вопросов. До заявлений о серверной выдаче нужно проверить прямой вызов, режим сессии в `finishExamSession`, подмену состава, отсутствие manifest и границы входных массивов.
5. **Частичные записи и гонки.** Попытки, итог и XP записываются несколькими запросами с компенсациями. Исключение, потеря связи или две вкладки могут оставить рассогласование. Требуется транзакционная операция и идемпотентность, затем аудит в той же транзакции.
6. **Cache-Control на гостевом редиректе.** Публичный ответ на dashboard гостя содержит `public, max-age=0, must-revalidate`; это не доказательство утечки личной страницы. Проверка авторизованных HTML/RSC, выхода и перехода между аккаунтами остаётся обязательной.

Это не полный аудит безопасности. Новые школьные роли, журнал действий и Desmos ещё не реализованы.
