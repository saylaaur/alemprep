## Привязка первого класса без новой миграции

[bootstrap-first-class.sql](bootstrap-first-class.sql) — данные, не DDL, не API.
Владелец проекта выполняет приватно заполненную копию в SQL Editor своего
Supabase проекта `euypaocjzcqlapfilrak` как postgres. Не предоставлять SQL Editor
или service-role учителю. Скрипт не создаёт пользователей, не меняет profiles.is_admin,
не выдаёт браузеру новые grants и не переводит существующего ученика этой школы в учителя.

Получить два UUID один раз:

~~~sql
SELECT gen_random_uuid() AS school_id, gen_random_uuid() AS group_id;
~~~

В приватной копии заменить каждый маркер `-- SET name` на присваивание;
school_id/group_id — те же UUID при повторе. Для существующей школы использовать
её настоящий UUID и точное название; новую школу не дублировать по имени.

~~~sql
v_school_id := 'UUID_FROM_QUERY';
v_group_id := 'OTHER_UUID_FROM_QUERY';
v_operator_email := 'COORDINATOR_EMAIL';
v_teacher_email := 'TEACHER_EMAIL';
v_school_name := 'Реальное название школы';
v_group_name := 'Реальное название класса';
~~~

Это фрагмент **внутри** BEGIN в DO; выполнить целиком заполненный файл.
Одиночную кавычку внутри SQL строки удвоить: `O''Brien`. Для kk отдельно заменить
объявление `v_locale TEXT := 'ru'` на `kk`; approved KK банк опубликован по AI review владельца.
Персональные emails/файлы не коммитить. Не запускать файл с placeholders.

Вся операция — одна транзакционная DO statement. Создаются школа, класс,
coordinator/teacher membership и group_teachers. Повтор неизменённой копии не
добавляет новую привязку/аудит. Другие школа/название/язык/активный учитель при том
же UUID отклоняются; строки с конфликтующими ролями не исправляются автоматически.
Ошибка отменяет и уже выполненные INSERT этого запуска. Существующий paused
класс/школа не включаются автоматически. Это узкий bootstrap, не управление LMS.
Отозванные coordinator/teacher membership или group_teachers блокируют повтор
с binding-withdrawn: сохранённый файл не используется для восстановления доступа.
Приёмка контента, tokens приглашений и назначения здесь не создаются.

## Проверка и открытие группе

1. Проверить реальный approved count выбранной темы (17 RU прогрессий приняты
   по exact hashes). Для следующих партий — [OPERATOR_GUIDE](translation-handoff/OPERATOR_GUIDE.md).
   Не включать trusted флаг
   на пустом банке; четыре технические задачи годятся для smoke, не полного пилота
   самостоятельной подготовки. Подготовить принятую тематическую подборку.
2. На reviewed SHA пройти CI и preview: RU/KK вход, своя группа учителя,
   отсутствие чужой группы, график/таблица на телефоне. Server-side service-role
   обязателен для trusted writes; значения секретов не показывать.
3. Учитель открывает `/ru/teacher` → свой класс → «Создать новый код».
   Код передаётся ученикам своей группы вне общего публичного чата; 72 часа,
   максимум 100 вступлений — предел кода, а не измеренная мощность сервера.
4. Ученик: Google → `/ru/join-class` → код → доступная тема → ответ → reload.
   Учитель проверяет ровно одну новую попытку и баллы в отчёте. Повтор ответа
   после обрыва сети не должен дублировать результат. Legacy результаты не
   объявляются подтверждёнными сервером и не импортируются в trusted отчёт.
5. Выпустить совместимый SHA с принятым RU каталогом; начать одной небольшой
   сопровождаемой группой (ориентир 10–20), с человеком на связи. Это организационный
   размер первого прогона, не результат нагрузочного теста. Через первую подтверждённую
   сессию расширять банк/группу, затем вторую группу/школу на выбранном RU или KK языке.

Если реальный вход/ответ/отчёт не проходит — не объявлять запуск успешным.
Сохранить код ошибки/время и совместимый SHA; не возвращать ученику score/XP grants.
