# Аудит, отчётность и кабинет учителя — требования пилота

08.09.2026. Дополнение по запросу пользователя. Это согласуемые требования к реализации, не описание уже работающей системы. Учительский кабинет и достоверная история обязательны до первого ученического занятия. Форму отчёта и адресата уточнит организатор.

## Три назначения данных

| Назначение | Источник | Доступ |
| --- | --- | --- |
| Учебные результаты | Подтверждённые сервером попытки/итоги с версией задания и назначения | Ученик — своё; учитель — свои назначенные группы |
| Аудит действий | Сервер/БД: выдача и отзыв роли, членство, назначение занятия, публикация/исправление контента, экспорт, исправление результата | Ограниченная операционная роль; учителю только нужная история своей группы |
| Работоспособность | Ошибки, длительность запросов, отказ сохранения, расходы, восстановление | Команда поддержки; без ответов, токенов, email и ФИО в логах |

Посещение страницы, открытие графика и длительность вкладки не доказывают обучение. Телеметрия браузера недоверенная. Числа для отчёта получаем из подтверждённых результатов; необязательная аналитика не блокирует урок.

## Сохранение и аудит

- У каждого подтверждённого результата: ID операции, серверное время, ученик, школа/группа и версия назначения на момент сдачи, версия вопроса, ответы/оценивание и версия алгоритма. Нельзя пересчитывать старую сдачу по сегодняшнему изменённому вопросу или сегодняшнему членству без явного правила.
- Повтор одной операции после потери ответа возвращает прежний исход. Такой же ID с другим содержимым отклоняется. Уникальные ограничения и транзакция предотвращают двойное начисление и дубли событий.
- Критическое событие и изменение данных фиксируются атомарно. Если обязательный аудит не сохранился, изменение не считается принятым. Асинхронную доставку во внешнюю систему при необходимости организовать через outbox; сбой внешнего приёмника не должен терять событие или создавать бесконечную очередь.
- Клиент не назначает автора, школу, роль, score и время подтверждения. Пользователи не могут UPDATE/DELETE журнал. Исправление — новое событие с причиной и ссылкой на предыдущую версию; отдельная процедура удаления данных соблюдает согласованные сроки хранения.
- Не обещать «неизменяемый даже администратором» журнал на одном Postgres с service-role. Ограничить доступ команды, регистрировать привилегированные изменения и, если модель угроз требует, хранить контрольные выгрузки отдельно с проверкой восстановления. Retention, полномочия и размещение согласуются в блоке 1.
- Тесты: 20 повторов → один результат/событие; сбой между итогом и аудитом → откат; ученик не пишет/удаляет аудит; отзыв учителя закрывает чтение и экспорт; смена школы не переносит старые результаты в чужой отчёт.

## Кабинет учителя: обязательный минимум

1. Только назначенные ему школы/группы, язык, список участников в необходимом объёме. Отдельная роль, не глобальный `is_admin`.
2. Назначить группе занятие из принятой программы: тема, RU/KK, состав/версия, даты. После начала менять через новую версию, сохраняя историю.
3. Видеть, кто начал и завершил, подтверждённые результаты и трудные темы. Отличать «нет данных», «не завершил» и нулевой балл. Состояние «есть несохранённый ответ» сервер не может знать при полном отсутствии связи — интерфейс не должен выдумывать его.
4. Получать сообщения об ошибках заданий; показывать статус обработки. Жалоба сама не переписывает оценку и публикацию.
5. Получать сводку за период и выгрузку по согласованной форме. Повторная проверка прав на сервере при каждой выдаче/скачивании; приватный кэш, ограниченный срок ссылки и отзыв доступа. Защита CSV от формул, если этот формат выбран.

Расписание всей школы, электронный дневник, чат родителей, произвольный конструктор тестов и выставление официальных оценок не входят в первый кабинет.

## Воспроизводимый отчёт для управления образования и команды

Предлагаемый первый формат: одна сводка по двум школам + приложения по разрешённым группам. Адресат получает агрегаты; индивидуальные результаты предназначены для уполномоченного учителя.

| Метрика | Определение |
| --- | --- |
| Приглашены / включены | Отдельные числа; включены по действовавшему в периоде членству, не все зарегистрированные на сайте |
| Активны | Уникальные участники с ≥1 подтверждённой учебной попыткой за период; вход сам по себе не активность |
| Завершение | Завершённые назначения / назначения с наступившим сроком, отдельно ученики и занятия |
| Возврат | Участники с подтверждённой работой в обеих сравниваемых неделях / участники первой недели; явно указать неполные недели |
| Входная/итоговая диагностика | Сопоставимые версии по одним темам; отдельно парные результаты, число участников и пропуски. Повторная сдача учитывается по заранее выбранному правилу |
| Качество сервиса | Успешные/неуспешные операции, время сохранения, инциденты, время восстановления; повторы сетевого запроса не считаются новыми занятиями |
| Качество контента | Обращения, подтверждённые ошибки, исправления по версиям и время обработки |

Каждая выгрузка содержит report ID, период `[начало, конец)`, часовой пояс `Asia/Almaty`, дату формирования, границу учтённых данных, фильтры школ/групп, версии правил и контента. Исключить demo/test аккаунты серверным признаком. Зафиксировать знаменатели, пропуски и поздние сохранения. Для точного воспроизведения хранить допустимый снимок агрегатов/источников по согласованному сроку; один повторный SQL по меняющейся базе недостаточен.

Обновлённый отчёт — новая версия с объяснением, старый не переписывается незаметно. Малые группы и пересекающиеся фильтры не должны позволять вычислить балл конкретного ребёнка. Порог раскрытия согласовать до экспорта. Рост среднего в двух школах не выдавать за доказанный причинный эффект платформы.

## Где реализовать

- Блок 1: карта данных, размещение и срок хранения результатов, аудита, отчётов и резервных копий.
- Блок 2: транзакционное сохранение, ограничения прямой записи, версия результата; серверный журнал через новую миграцию и `types/db.ts`.
- Блок 4: `lib/supabase/pilot-actions.ts`, `lib/supabase/queries.ts`, новые модули отчётности и тесты, кабинет в `app/[locale]/(app)/teacher/`, RU/KK. Пути и SQL-контракты детализировать после проверки схемы.
- Блок 6: лимиты выгрузок, пагинация, планы запросов/индексы, ёмкость аудита, резервирование и восстановление. Тяжёлый отчёт не должен исчерпывать ресурсы сохранения урока.
- Блок 7: тестовая группа с заранее известными числами → сверка каждой метрики и выгрузки; затем восстановление копии → тот же принятый отчёт.
