# AlemPrep: runbook для live demo

Дата демо: 28 августа 2026 года.

Ответственный за показ: друг на своём ноутбуке. Ответственный за релиз и Supabase: владелец проекта.

## Критерий готовности

Демо можно проводить, когда выполнены все пункты P0:

- [ ] Известен точный публичный URL и он открывается с ноутбука ведущего.
- [ ] Подготовленный аккаунт входит через Google и не показывает личные данные владельца проекта.
- [ ] В аккаунте завершён онбординг, выбрана пара предметов и есть данные для дашборда и прогресса.
- [ ] Создана или подтверждена резервная копия базы до применения миграций.
- [ ] Новые security-миграции применены к нужному Supabase-проекту.
- [ ] Задеплоена версия приложения с серверной проверкой ответа и защитными HTTP-заголовками.
- [ ] Supabase Security Advisor повторно запущен, критические замечания просмотрены.
- [ ] Пройден smoke-тест на ноутбуке ведущего, а не только на ноутбуке разработчика.
- [ ] Подготовлены мобильный интернет и запись экрана как два независимых фолбэка.

Регистрацию пользователей не отключать. После релиза проверить и вход подготовленного пользователя, и новый Google-вход.

### 2. Сделать резервную копию Supabase

MFA для административного аккаунта Supabase уже включена. На скриншоте подключён один Google Authenticator; добавить второй фактор или безопасный резервный способ доступа, чтобы потеря одного телефона не заблокировала проект.

Проверка управляемых бэкапов:

1. Открыть Supabase Dashboard и выбрать проект `euypaocjzcqlapfilrak`.
2. Открыть `Database` → `Backups`. Название пункта может отличаться в обновлённом интерфейсе.
3. Проверить время последней успешной копии и доступный способ восстановления для текущего тарифа.
4. Сохранить время проверки в заметках релиза. Не считать наличие вкладки доказательством восстановления.

Ручной логический экспорт перед миграциями:

1. В Supabase открыть `Connect` и взять прямую или session-pooler строку подключения Postgres.
2. Не вставлять пароль в чат, issue, скриншот или историю команд на демонстрационном экране.
3. На доверенном компьютере с `pg_dump` выполнить:

```bash
mkdir -p backups
pg_dump --format=custom --no-owner --no-acl \
  --dbname='<SUPABASE_DATABASE_URL>' \
  --file='backups/alemprep-pre-demo-2026-08-27.dump'
```

4. Проверить, что файл существует и имеет ненулевой размер:

```bash
ls -lh backups/alemprep-pre-demo-2026-08-27.dump
pg_restore --list backups/alemprep-pre-demo-2026-08-27.dump | head
```

5. Хранить файл вне Git и не отправлять его другу. Дамп содержит данные пользователей и ответы.

Полезная справка: [Supabase Database Backups](https://supabase.com/docs/guides/platform/backups) и [Supabase production checklist](https://supabase.com/docs/guides/deployment/going-into-prod).

Если экспорт не удалось создать, не применять миграции вслепую. Для live demo можно оставить текущую базу и честно не заявлять, что новые DB-защиты уже работают.

### 3. Применить только новые security-миграции

После готового дампа:

- [ ] Проверить содержимое `supabase/migrations/0020_profile_privilege_hardening.sql`.
- [ ] Проверить содержимое `supabase/migrations/0021_ai_quota_hardening.sql`.
- [ ] Убедиться, что проект и окружение выбраны правильно.
- [ ] Применить миграции штатным способом команды проекта.
- [ ] Не запускать старый `supabase/migrations/run_all.sql`: он не является актуальным комплектом всех миграций.
- [ ] Не редактировать уже применённые миграции.

Если локальная история Supabase CLI точно синхронизирована с удалённым проектом, использовать:

```bash
npx supabase migration list
npx supabase db push
```

Если история расходится, не чинить её в спешке. Открыть SQL Editor и применить только содержимое двух новых файлов по очереди. Сохранить результат каждого запуска.

После применения проверить отдельным обычным тестовым пользователем:

- [ ] Пользователь не может изменить `profiles.is_admin`.
- [ ] Неверный ответ не сохраняется как верный и не начисляет XP.
- [ ] Пользователь не может сбросить свой AI-счётчик прямым обновлением таблицы.
- [ ] Обычная практика и AI-помощь продолжают работать.

### 4. Запустить Security Advisor

1. Открыть Supabase Dashboard → `Advisors` → `Security Advisor`.
2. Запустить повторную проверку после миграций.
3. Открыть каждую ошибку уровня error/critical. В первую очередь проверить:
   - RLS включён на всех таблицах в открытых схемах;
   - нет таблиц с личными данными и широким доступом `anon` или `authenticated`;
   - нет опасных `SECURITY DEFINER` функций, доступных неподходящей роли;
   - у функций задан безопасный `search_path`, если Advisor это требует;
   - нет политик, позволяющих пользователю менять роль или глобальный лимит.
4. Сохранить скриншот или текст оставшихся предупреждений без секретов.
5. Не нажимать автоматическое исправление, пока не понятен SQL и влияние на вход и практику.

Справка: [Supabase Security Advisor](https://supabase.com/docs/guides/database/database-advisors) и [Secure your data](https://supabase.com/docs/guides/database/secure-data).

### 5. Проверить Auth и регистрацию

- [ ] `NEXT_PUBLIC_SITE_URL` равен `<DEMO_URL>`, без localhost.

## Live-flow на 5–7 минут

1. Лендинг, 20–30 секунд.
2. Дашборд и персональный план, 40–50 секунд.
3. Одна задача: ответ, Enter, разбор, фокус-режим, 70–90 секунд.
4. AI-подсказка, до 25 секунд, только если она проверена.
5. Прогресс и недельная траектория, 40–50 секунд.
6. Стартовый экран пробника, 30–40 секунд.
7. Статус, безопасность и запрос к аудитории, 60–80 секунд.

Не запускать новую диагностику или 160-минутный пробник. Подготовленный результат показывает функцию быстрее и надёжнее.

## Фолбэки

### Нет интернета

1. Переключиться на hotspot.
2. Если сайт не открылся за 15 секунд, запустить локальную запись.
3. По записи рассказать тот же маршрут. Не тратить минуту на перезагрузки.

Фраза:

> Сеть на площадке нестабильна, поэтому покажу запись того же сценария с рабочего production URL. После выступления дам ссылку для самостоятельной проверки.

### Не проходит Google OAuth

1. Не менять OAuth-настройки со сцены.
2. Использовать уже открытую авторизованную вкладку.
3. Если сессия потеряна, показать лендинг и запись защищённой части.

### AI не отвечает

1. Ждать не больше 10 секунд.
2. Закрыть панель и показать встроенный пошаговый разбор.

Фраза:

> AI работает через внешний API и сейчас не ответил. Основной разбор хранится в платформе и не зависит от генерации, поэтому ученик всё равно получает объяснение.

### Demo-задача оказалась неверной или сломанной

1. Не спорить с интерфейсом.
2. Сказать, что задача попала в очередь редакторской проверки.
3. Перейти к заранее подготовленной второй теме или записи.

Фраза:

> Этот пример показывает, зачем мы отделяем автоматическую генерацию от публикации. Перед пилотом банк проходит ручную редактуру. Перейду к проверенному примеру.

### Пустой дашборд или прогресс

Использовать подготовленную вкладку или запись. Не создавать данные со сцены.

### Ошибка deployment

Откат выполнять только человеку, который знает последний зелёный deployment. Ведущий продолжает питч по записи и не открывает технические панели.

## Что остаётся за рамками завтрашней демонстрации

Эти риски нельзя честно назвать закрытыми одним вечерним релизом:

- полное отделение ключей правильных ответов от данных, доступных клиенту;
- запрет прямой записи `attempts`, XP и стрика через пользовательский API Supabase;
- ручная редактура и приёмка банка заданий;
- политика конфиденциальности, согласия родителей, удаление и экспорт данных;
- юридическое решение по хранению данных граждан Казахстана и трансграничной AI-передаче;
- error tracking, аварийные экраны и проверенное восстановление из бэкапа;
- e2e-тесты, слабая сеть и полноценная мобильная приёмка.

Успешное live demo подтверждает, что пользовательский сценарий работает на площадке. Оно не заменяет production-аудит перед пилотом в школе.
