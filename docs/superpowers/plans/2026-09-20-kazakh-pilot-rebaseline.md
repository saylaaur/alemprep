# Казахский контент и школьный пилот — пересмотр 20 сентября 2026

> Для исполнителя: применять `superpowers:executing-plans`, одна карточка за проход. Этот документ меняет выбор источника контента и ближайшую очередь. Контракты серверного обучения, прав, отчётов и эксплуатации из планов 01–09 сохраняются. Статусы ниже не являются новым runtime review.

**Цель:** провести ограниченные занятия в двух сельских школах с проверенными заданиями на казахском, достоверным сохранением и воспроизводимой сводкой. Не ждать перевода всего банка или государственного финансирования.

**Решение:** небольшой банк из казахских оригиналов — допустимый основной маршрут после проверки образца и условий использования. Не покупать автоматически десять пробников и не размножать каждую задачу. Google NMT сохранить для недостающих тем и дальнейшего расширения. Предварительный scope: математика, 2–3 темы, сначала 20–30 кандидатов, затем 50–80 принятых заданий. Предмет/темы ещё должен подтвердить учитель.

## 1. Оценка вариантов

| Вариант | Польза | Цена и ограничения | Решение |
| --- | --- | --- | --- |
| Перевести небольшой выбранный RU-набор | Инструмент уже написан; низкая стоимость API | Русский оригинал тоже требует предметной проверки; казахский перевод нужно вычитать | Запасной маршрут для пробелов; не выбрасывать |
| Казахские оригиналы с разрешённым использованием | Есть исходная терминология; можно согласовать с учителем | Покупка экземпляра не подтверждает право публикации; OCR/ответы/рисунки требуют сверки | Предпочтительный эксперимент на одном образце |
| Десять пробников → массовые AI-варианты | Потенциально много кандидатов | Неизвестны покрытие, дубли, стоимость проверки; новые числа могут ломать решения и единственность ответа | Не стартовать массово до приёмки маленькой партии |

Генерация сама по себе не устраняет ограничения использования исходника. Перед копированием/переработкой материалов зафиксировать применимые условия с правообладателем; при отсутствии разрешения — собственные задания по учебным навыкам или лицензированные материалы. Не заявлять сгенерированные задания официальными заданиями НЦТ. Основание для проверки прав: [закон РК, в частности статьи 6, 16, 31](https://www.adilet.zan.kz/rus/docs/Z960000006_).

## 3. Что меняется в продукте и что сохраняем

- Казахский вопрос может быть самостоятельным оригиналом: ему не нужна фиктивная RU-запись и `source_question_id`.
- RU/KK интерфейс остаётся двуязычным. Для ограниченной программы обязательна проверка каждого реально назначенного языка. KK-only программа допустима только после подтверждения школьных потребностей; если нужен RU, подготовить отдельный принятый набор. Равное число RU/KK и пары для каждого задания не являются предварительным условием KK-занятия.
- Не подменять KK русским текстом. Серверная программа фиксирует locale и версии, недоступные темы не назначаются. Переключение языка не меняет язык/ключи уже выданной сессии.
- Одна content/version/publication система для оригиналов, переводов и собственных вариантов. Сохраняем аудит, safe DTO и серверный scoring; новый путь импорта не обходит их.
- Независимое новое задание получает свою family; перевод и ревизия сохраняют соответствующую связь. Для близких параметрических вариантов применять согласованную family/reward policy, не создавать новые families ради повторного XP.
- Desmos, AI, полный пробник и дополнительные режимы не входят в первый сопровождаемый урок. Их серверное отключение ещё нужно реализовать и проверить.
- Кабинет учителя остаётся целью. На первом сопровождаемом уроке допускается операторская сводка по подтверждённым данным в пределах прав школы; самостоятельный пилот требует S/R UI.

## 4. Почему старые скрипты нельзя просто запустить

`scripts/insert-to-db.ts`: RU-путь принимает GeneratedQuestion и пишет `language='ru'`; KK-путь принимает TranslatedQuestion с RU lineage. Есть `--publish` и запись через service role. Это не безопасный импорт native-KK в approved version catalog.

`scripts/generate-variants.ts` / `scripts/verify-questions.ts`: платные model calls, старые model defaults и стоимость в коде; ограничение суммы до отправки для нового запуска не доказано. `scripts/transcribe-questions.ts` содержит правила пропуска изображений, преимущественно по русским признакам. Не считать казахскую диаграмму распознанной только потому, что извлечён текст.

Новый маршрут: закрытый исходник → сверенный draft → независимое решение/языковая приёмка → dry-run импорта → versioned draft → явная публикация выбранных версий → программа. Не запускать `gen:all`, `gen:insert --publish` или платную генерацию по этому документу.

## 5. Очередь работы и выход каждой карточки

### K00 — выбрать материал и программу, без разработки и оплаты API

**Файл:** `docs/pilot/KAZAKH_SOURCE_INTAKE.md`. Ответственные: основатель/друг и учитель.

- [ ] Получить поставщика, цену одного/десяти пробников, предмет, год, перечень тем, наличие ключей/решений и формат PDF/фото.
- [ ] Зафиксировать разрешённое использование: хранение, показ ученикам, переработка, отправка провайдеру OCR/AI; закрытые условия хранить вне публичного Git.
- [ ] Учитель выбирает 2–3 темы первых занятий и проверяет 20–30 кандидатов из образца. Включить формулы, отрицания, варианты, таблицу/рисунок при их наличии; недостающий материал исключить из программы, не угадывать.
- [ ] Сравнить с малой переводной подборкой: принятые задачи по темам, минуты проверки на задачу, доля брака, стоимость принятого задания. Если казахский источник не доступен/не подходит, использовать C00b sample с отдельным бюджетом.
- [ ] Только после sample решать, нужны ли ещё девять пробников. Оплата Google не является зависимостью K00 или серверной разработки.

**Приёмка:** источник и условия зафиксированы, reviewer назван, образец оценён, есть матрица тем. До этого цена генерации и дата урока не считаются определёнными.

### K01 — native-KK private drafts и lineage на synthetic fixtures

**Depends:** контракт K00; реальные материалы не нужны для synthetic разработки. **Files:** NEW `scripts/lib/native-kk-draft.ts`, `.test.ts`, `scripts/prepare-native-kk.ts`; REUSE `scripts/lib/schema.ts`, `checks.ts` и `lib/content/versions.ts`.

- [ ] Зафиксировать строгий draft contract: stable source ID/hash, номер задания, locale=kk, subject/topic, body/explanation, asset refs/hashes, origin (`licensed-original`/`authored`/`generated-variant`), optional parent draft ID и private rights evidence reference. Review хранится отдельно от model output и привязан к content hash; модель не выставляет approved.
- [ ] Тесты: native KK без RU source допустим; неизвестный topic, потерянная таблица/asset, неверные option IDs и неподтверждённое происхождение дают явный reject/manual review; повтор сохраняет stable identity, изменение hash снимает review.
- [ ] CLI по умолчанию только читает локальный приватный JSON и пишет draft/report. Нет DB-клиента, API-сети, auto-publish; реальные PDF/ответы не коммитить.
- [ ] Добавить разбор структурных ошибок и сводку по темам. Проверки типов/скриптов и targeted tests. Synthetic pass не является языковой приёмкой.

**Выход:** валидируемый закрытый draft artifact для K02/K03. Сначала typed contract и tests, затем parser; никакой новой DB migration ради формата файла.

### K02 — небольшая редакторская партия; генерация только при необходимости

**Depends:** K00, K01; проверяющий и отдельный лимит API при вызове модели.

- [ ] Извлечь 20–30 исходных задач и сверить с оригиналом; сохранить OCR-неуверенность/ссылки на рисунки. Не размножать OCR-ошибки.
- [ ] Если исходные задачи можно использовать, начать с них. Если нужны собственные, создать 5–10 пробных вариантов по выбранным навыкам и независимо решить каждый. Изменение чисел без пересчёта ответа запрещено.
- [ ] Проверить каждый правильный/неправильный вариант, ОДЗ, единицы, объяснение, таблицы/рисунки и казахский язык. LLM-verifier — вспомогательный сигнал, не human acceptance.
- [ ] Если понадобится API-код, отдельно расширить генератор locale=kk, dry-run, preflight cost reservation, token/output/concurrency/retry caps и checkpoint. Тест: бюджет закончился → следующий request не отправлен; uncertain response не вызывает слепой повтор. Старые defaults не подтверждают современный тариф.
- [ ] Масштабировать до 50–80 принятых задач только после sample. Для планирования: 3 темы × 15–20 задач + 5–20 резервных, а не произвольное число пробников.

**Выход:** hash-bound signed-off batch + rejected list + стоимость/минуты редактора. При критической ошибке sample пересмотреть процесс и перепроверить затронутый класс задач.

### K03 — идемпотентный импорт и программа по версиям

**Depends:** L01, E02, K01; для реальной публикации K02. Интеграция выдачи ждёт L02c/L04.
**Files:** NEW `scripts/import-reviewed-content.ts`, `scripts/lib/reviewed-content-import.ts`, `.test.ts`, `tests/db/reviewed-content-import.test.ts`; REUSE `lib/content/versions.ts`, `public-question.ts`, будущие C01/C02 program/publication contracts.

- [ ] Dry-run сверяет batch hash, права/предметную/языковую приёмку, тему/locale, контексты/медиа и lineage. Прямой `--publish` из старого importer не использовать.
- [ ] Import создаёт versioned drafts. Exact batch retry не дублирует вопросы/контексты; changed content создаёт новую ревизию без изменения исторических попыток. Реальные mutations только после synthetic DB acceptance и конкретного списка партии.
- [ ] Отдельный publish публикует только принятые hashes/version IDs; изменённый draft, отсутствие media или review блокируют операцию. Quarantine отзывает новую выдачу и сохраняет историю.
- [ ] Тесты DB: native-KK без фиктивного RU; draft недоступен ученику; retry; partial failure rollback; stale review rejected; одинаковая транскрипция не получает двойной reward family; safe DTO не содержит correct/explanation до разрешённого раскрытия.
- [ ] C01 фиксирует программу по version IDs и locale. E2E на школьном маршруте проверяет таблицы/формулы/рисунки/объяснения и отсутствие русских подстановок.

**Выход:** допуск контента SP4. Общая архитектура/номера миграций — по текущему L02a-R base; не занимать старые зарезервированные номера. Новая migration только при доказанной нехватке схемы.

### Техническая очередь, которая не зависит от покупки

1. Восстановить отдельный checkout `3f4c5a2`; закрыть перечисленные в §2 пробелы L02a-R tests и пройти отдельный review. Исторические зелёные тесты не переиспользовать как свежий gate.
2. L02b → L02c → L02d: reward invariants, реальный start/state, server grading/receipt/review. Затем L03a–d/L04: переключение режимов, закрытие обходов. Нельзя дать детям legacy writes ради срока.
3. S/O: participants, принадлежность школе, серверная программа/режимы и отзыв прав. Одна группа в первой школе, затем вторая.
4. R/U: сверяемая сводка, retry/reload, общий компьютер/logout, слабая сеть. Полный UI учителя — до самостоятельного использования.
5. O/P: monitoring, лимиты, нагрузка на согласованном стенде, фактическое восстановление backup, release SHA/schema и школьная репетиция. SP0–SP7 должны иметь evidence.

K00–K02 могут идти одновременно с технической очередью организационно; не запускать параллельно DB reset/test процессы на одном Docker. Взаимозависимости полного плана сохраняются, это не разрешение пропускать нужные S/R/U/O задачи.

## 7. Государственное финансирование и доказательства пользы

Финансирование — возможный последующий этап, не предпосылка первой апробации и не обещанный результат встречи. Просить смету на создание/лицензирование и методическую проверку казахского банка, обучение учителей, поддержку/эксплуатацию, доступность и измерение результатов. Стоимость API перевода показывать отдельной небольшой строкой; не представлять её как главный финансовый барьер.

До заявки собрать фактические занятия/уникальных участников/завершение с явными знаменателями, повторное использование, ошибки контента, минуты учителя и стоимость принятой задачи. Короткий пилот не доказывает рост ЕНТ; никаких причинных обещаний по 1–2 урокам. Согласие школы на пилот не равно обязательству государства заплатить.
